# 许可证分档与商用边界速查

选型时最不可逆的决策就是许可证。以下分档用于 `score.py` 的自动分类，也用于人工复核。

## 一档：宽松（Permissive）— 可闭源商用

| SPDX | 名称 | 关键义务 |
|---|---|---|
| MIT | MIT | 保留版权声明与许可声明 |
| Apache-2.0 | Apache 2.0 | 保留声明 + **专利授权** + 标注修改 + NOTICE 文件 |
| BSD-2-Clause / BSD-3-Clause | BSD | 保留声明（3-Clause 额外禁止用项目名背书） |
| ISC | ISC | 保留声明 |
| Unlicense / CC0-1.0 | 公共领域 | 无实质义务 |

**结论**：可以闭源商用，可以拿来做付费产品的底座。**首选。**

## 二档：弱 Copyleft — 有限制的可商用

| SPDX | 名称 | 关键边界 |
|---|---|---|
| LGPL-3.0 / LGPL-2.1 | LGPL | **动态链接**你的代码可闭源；静态链接需提供 LGPL 部分源码 |
| MPL-2.0 | Mozilla Public License 2.0 | **文件级** copyleft：改动的那个文件要开源，其他文件不受影响 |
| EPL-2.0 | Eclipse Public License | 与 MPL 类似，文件级 |

**结论**：可商用，但改动边界要盯住。**改核心文件 = 那个文件要开源。**

## 三档：强 Copyleft — 服务化即触发开源

| SPDX | 名称 | 关键边界 |
|---|---|---|
| AGPL-3.0 | GNU Affero GPL | **通过网络提供服务即触发开源义务**，即使没分发二进制 |
| GPL-3.0 / GPL-2.0 | GNU GPL | 分发衍生作品时须开源全部衍生部分 |

**这是最容易踩雷的一档。** 典型陷阱：
- 用 AGPL 项目搭了个 SaaS，没开源 → 违反 AGPL
- AGPL 项目自己用了，但没在网络服务场景下用 → 不触发

**结论**：**对外提供服务前必须先解决授权**。两条路：① 按 AGPL 开源你的服务 ② 联系作者买商业许可（通常贵但一劳永逸）。

## 四档：Source Available — 看得见但不能用

| 许可证 | 典型项目 | 关键边界 |
|---|---|---|
| Sustainable Use License | n8n | 可自用可商用，**不得用于对外服务/转售宿主形态** |
| BSL-1.1 | CodePilot（歸藏） | **100 人以上组织或商用需单独购买授权** |
| BUSL-1.1 | 部分数据库 | 生产环境使用需授权，有时间窗 |
| SSPL-1.0 | MongoDB | 服务化即视为分发 |
| Elastic License 2.0 | Elasticsearch | 不得提供为托管服务 |
| Dify Open Source License | Dify | 基于 Apache 2.0，附加多租户限制 |

**GitHub 的 `spdx_id = "noassertion"` 就是这一档的标记。** 常见于大型项目自定义许可证。

**结论**：**自用没问题，做产品要先读原文。** 这一档是最容易被误判的——因为项目看起来"开源友好"（有 source code、有 issue），但商用边界跟 Apache 完全不同。

## 五档：无许可证 — 默认不可商用

**仓库没有声明 LICENSE 文件时，著作权默认保留。** GitHub 上代码公开 ≠ 授权你使用。

- 法律上：默认「保留所有权利」，只有明确许可才授权
- 实践上：绝大多数知名项目会加 LICENSE，**没有 LICENSE 的往往是个人小项目或刚上传**

**结论**：除非项目作者明确授权，否则不要用于任何商业用途。

## 复核清单

拿到一个候选方案，按这 5 条过一遍：

1. `LICENSE` 文件存在吗？仓库首页有没有许可证徽章？
2. GitHub API 返回的 `license.spdx_id` 是什么？若是 `noassertion` → 进自定义档
3. 是不是 AGPL？→ 做服务化前必须解决
4. 是不是 BSL / Sustainable Use？→ 商用要单独授权
5. **README 里有没有额外的商用限制条款？**（这一条最容易被忽略——有些项目在 README 而非 LICENSE 里写限制）

## 为什么这件事值得单独做一层

前面实证过：开源自带的「参考资料重打包」有明确先例（GitHub 1.2 万星项目重组成 601 条决策清单，19.1 万赞）。**但那条路径里没有许可证维度**——而对要真拿去做产品的人，许可证是最硬的约束。

**补上这一维，就是从「资料」变成「能直接做决定」。**
