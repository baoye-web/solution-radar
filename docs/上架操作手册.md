## §1 一次性人工断点（你需操作，约 20 分钟）

### 断点 1：登录开放平台

1. 浏览器打开 https://open.workbuddy.cn/login/
2. 微信扫码登录（或手机号 + 验证码）
3. 登录后访问 https://open.workbuddy.cn/ ，确认能看到「控制台」

### 断点 2：开发者实名认证

进入「设置 → 开发者认证」，按提示提交：

| 项 | 要求 |
|---|---|
| 真实姓名 | 与二代身份证一致 |
| 身份证号 | 仅支持中国大陆二代居民身份证 |
| 手机号 | 已实名 |
| 邮箱 | 可收验证码 |
| 人脸核身 | **需要一部能完成人脸识别的手机** |

⚠️ **一个身份证在全平台只能认证一个个人主体，换账号无法绕过。**

### 断点 3：开发者资料

「设置 → 开发者信息」：

| 字段 | 要求 |
|---|---|
| 头像 | 512×512 px，≤500KB，JPG/PNG |
| 昵称 | 全平台唯一，2–20 字符。**不得含**「官方/平台/客服/管理员/认证/VIP/第一/独家/保证/测试/试用」等词 |
| 简介 | 20–120 字符 |
| 联系方式 | 至少 1 项，最多 5 项 |

### 断点 4：微信扫码签约（开通收款）

**顺序铁律：先过审 → 再开户 → 后定价。**

需要先有 ≥1 个审核通过的 Skill/专家才能开通收款账户。所以先做 §2.1 提交审核，等通过后再回来做这一步。

## §2 之后就是全自动

### §2.1 提交审核（脚本可代劳）

先取登录态。在浏览器 DevTools → Network → 任一请求 → 复制：

- `Cookie` 请求头完整值
- `X-Party-Id` 请求头值

然后：

```bash
export WB_COOKIE='session=xxx; ...'
export WB_PARTY_ID='<x-party-id>'

cd ~/ego/auto-income-20261030/agent-radar

# 提交审核
python3 solution-radar/scripts/publish-to-openplatform.py \
  --skill-dir ./solution-radar --submit
```

脚本会依次完成：本地预检 → 打包 zip → init-upload → PUT 文件 → complete-upload → 提交审核。

**如果 Cookie 失效**，脚本会明确报 `登录态失效`，重新取一次即可，不需要改代码。

### §2.2 查审核状态

```bash
# 平台会发通知（微信最迟 24 小时内返回审核结果）
# 也可查资产列表
python3 solution-radar/scripts/publish-to-openplatform.py --skill-dir ./solution-radar
```

**驳回后的正确做法**（开发者公约 2.1.2）：必须真正修改内容再重提，**禁止无修改重提**。最常见的驳回原因是：

| 驳回原因 | 对应改法 |
|---|---|
| 2.3.1 空壳/无实质内容 | 补真实用例与可运行示例 |
| 2.2.1 名称堆砌热点词 | 改成纯功能性命名 |
| 2.8.3 接口使用安全 | 检查是否有自动化替代用户真实操作的行为 |

### §2.3 定价与发布（审核通过后）

```bash
# 一次性买断 79 元
python3 solution-radar/scripts/publish-to-openplatform.py \
  --skill-dir ./solution-radar --price 79 --publish

# 或按月订阅 19 元
python3 solution-radar/scripts/publish-to-openplatform.py \
  --skill-dir ./solution-radar --price 19 --monthly --publish
```

⚠️ **付费方式发布后不可更改。** 官方示例价是 79 元一次性；市场上已有 19 元/月、29 元买断的真实成交案例。

### §2.4 开通收款 + 提现（微信侧，需人工）

1. 后台开通收款账户 → 填资料 → **微信扫码签约**
2. 收益到账后在后台点提现 → **跳转微信确认**

## §3 定价策略与理由

| 项 | 建议 | 依据 |
|---|---|---|
| 定价 | **19 元/月** 或 **79 元买断** | 官方示例 79 元；市场已有 19 元/月、29 元买断案例 |
| 分成 | 内测期平台服务费 **1%** | 多方一致；官方文档未写具体数字，以后台实时显示为准 |
| 结算 | 微信提现 | 个人路径无银行卡提现记载 |

**先免费上架还是先收费？**

建议**先 19 元/月**，不要先免费。理由：
- 平台有「重复铺量」条款（公约 2.6.2）：仅改变免费/付费状态不算实质差异
- 付费用户的安装量、调用量、留存率是运营数据看板的核心指标，直接影响后续推荐
- 免费用户不会给你任何可用于改进的信号

---

## §4 付费 skill 不会被优先推荐（这点必须知道）

平台官方文档、开发者公约、前端接口、推广分析 API **全都没有**「付费加权/优先推荐」的说明。

- `/docs/monetization` 通篇只讲发布与收款，无一句涉及回答内曝光
- 运营数据看板的指标只有：安装量、调用量、留存率、错误率 —— **没有「曝光量」「排序」**
- 推广分析 API 的漏斗只有 `clicks → installs → newUsers`，**没有推荐位维度**
- 开发者公约 2.5.3 明确**禁止**把付费榜单伪装成平台官方推荐

**推论**：**付费买到的是使用权，不是曝光位。**

所以流量必须从外部来 —— 这正是 GitHub 仓库 + 每日更新的存在意义：它是唯一不依赖平台分发的资产。

**待验证的第一件事**：上架后安装自己的付费 skill，问 Agent 一个它本该被调用的场景，看它是否出现。**这个测试必须在第 4 周做**，因为它决定整条路径的天花板。

## §5 风险与对冲

| 风险 | 概率 | 对冲 |
|---|---|---|
| 审核被驳回 | 中 | 预检已覆盖 8 个必填字段 + 目录结构 + 体积；驳回必真改再重提 |
| 付费 skill 不被优先调用 | 中高 | 仓库 + 站点 + 内容分发做外部流量；skill 是变现承接而非唯一入口 |
| 上架三个月零成交 | 中 | 定价低（19 元）先验证需求；每周看推广数据看板的 clicks→installs 漏斗 |
| 竞品复制 | 低 | 许可证分档 + 四维清单的具体口径是可积累的运营资产；纯 GitHub 榜单任何人都能拉，但没有人在上面加「代价/红线」维度 |
| GitHub API 限流 | 低 | 带 token 5000 次/小时；脚本内置退避重试；失败时留 artifact |
| 内容同质化 | 中 | **必须持续补充「红线」维度的人工核对结论**——这是最难被自动复制的一块 |
